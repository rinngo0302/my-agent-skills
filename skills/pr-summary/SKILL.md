# PR Summary

このスキルが読み込まれたら「PR-Summaryコマンドを読み込みました」と出力してください。

現在の変更をコミットし、プルリクエスト本文を生成して表示します（PRは実際には作成しません）。

## 実行条件

- Git 管理されたリポジトリ内で実行すること
- `git` コマンドが利用できること（`git status` / `git diff` / `git log` / `git branch`）
- PR 本文テンプレート参照のため `.github/pull_request_template.md` が存在すること（存在しない場合は通常フォーマットで生成）
- コミットを伴うため、ユーザーがコミット実行を許可していること
- リモート確認や既存 PR 確認を行う場合は `gh` コマンドが利用可能であること
- ワークツリーに未保存の衝突状態（コンフリクト未解消）がないこと

## ワークフロー

### 1. 事前確認と状態把握

1. 現在のブランチ名を表示する
2. `git status` と `git diff` で変更内容を確認する
3. ステージ済みファイルと未ステージファイルを分類する
4. 未ステージファイルはそのまま残す（勝手にステージしない）
5. 変更サマリーをユーザーに提示し、このブランチで進めてよいか確認する

### 2. コミット戦略

コミットは以下のルールに従って行う：

- **Conventional Commits** 形式でコミットメッセージを作成する（`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:` など）
- 目安: 1コミットあたり 1〜3 ファイル、機能/画面単位で分割する
- 未ステージ変更が関連している場合のみ、ユーザーにステージ提案を行う
- コミット前にユーザーへメッセージを提示して確認を取る

### 3. PRターゲットブランチの決定

1. 既存ブランチ一覧を取得する（例: `git branch --format='%(refname:short)'`）
2. AskUserQuestion の choices を使い、矢印で選択できる形でターゲットブランチを確認する
3. ブランチ名が規約に合わない場合は警告し、最終確認を取る

### 4. PR本文の生成（作成はしない）

1. `.github/pull_request_template.md` が存在する場合は読み込み、テンプレートに沿って本文を構成する
2. テンプレートが存在しない場合は以下のデフォルトフォーマットで生成する：

```
## 概要
（変更の目的と背景を3〜5行で説明）

## 変更内容
- （主な変更点を箇条書き）

## 動作確認
- （確認した内容）

## その他
（補足事項があれば）
```

3. コミットログと差分から要点を抽出し、WHY（なぜ必要か）を明示する
4. 技術的判断がある場合は理由を簡潔に記載する
5. 必須情報以外は削り、冗長にしない
6. UI変更がある場合はスクリーンショット添付を提案する
7. **PRは作成せず、本文テキストのみをチャットに表示する**

## 品質基準

- 変更全体が短時間で把握できる要約になっている
- 「なぜ必要か」が明確である
- 実装上の判断理由が追える
- 無関係な情報が混入していない
- 「Generated with Claude Code」などの署名は含めない

## エラーハンドリング

- コミット失敗時: 競合や pre-commit hook エラーを報告し、解決策を提案する
- PR本文生成時の問題: 原因を示し、手動で本文を組み立てる手順を案内する
- リモートブランチがない場合: `git push -u origin <branch>` を提案または実行する
- 既存PRがある場合: 警告し、既存PR更新方針を提案する

## 注意事項

- **未ステージのファイル**: 関連性が高い場合のみ自動ステージを提案する
- **PRは実際に作成しない**: 本文テキストのみをチャットに出力して完了とする
- コミット前にユーザーへ確認を取ること（破壊的操作のため）
