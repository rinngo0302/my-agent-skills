# Commit Plan

staged差分だけを対象に、計画と実行を明確に分ける。

## 計画

1. Gitリポジトリ内であることを確認し、`git status`、`git diff --cached`、直近の`git log`を読む。staged差分がなければ、その旨を伝えて終了する。
2. 変更を目的と依存関係で整理する。ファイル種別ではなくレビューしやすさを優先し、次の基準で分割する。
   - **1コミット＝レビュワーが独立して確認・判断できる1項目（1つの変更目的）**を原則にする。「何を、なぜ変えたか」を1つの具体的な目的で説明できる粒度まで分割する。
   - 同じ機能・画面・ファイルに属していても、それだけを理由にまとめない。独立した振る舞いの追加、バグ修正、リファクタリング、表記修正など、別々にレビューできる項目は分ける。同一ファイル内でも必要に応じてhunk単位で分割する。
   - 「○○対応」「関連修正」のような広い見出しで複数の目的を束ねない。例えば、入力検証の追加と表示順の修正は、同じ画面でも別コミットにする。
   - 機能が完成していない途中段階でも、エンティティや基盤レイヤーなど単独でレビューできる単位は独立させてよい。
   - 実装とテスト、必須設定など、分けると変更意図や成立性を損なうものは同じコミットに含める。
   - 各コミットが、差分を読んだ限りコンパイルエラー、参照切れ、明白な不整合を生まない順序にする。
   - 計画提示前に各コミットを見直し、独立して判断できる項目が複数混ざっていれば再分割する。まとめる場合は、分けると変更意図や成立性を損なう具体的な理由を「分割理由・依存関係」に示す。コミット数を減らすことより、レビュワーの理解しやすさを優先する。
3. ビルド、テスト、lint、型チェックは実行しない。成立性はコードと差分の静的確認だけで判断し、判断できない点は懸念として示す。
4. メッセージは[Conventional Commits 1.0.0](https://www.conventionalcommits.org/ja/v1.0.0/)に従う。型、scope、本文の使い方と言語は既存履歴に合わせ、傾向を判断できなければ日本語にする。破壊的変更は`!`または`BREAKING CHANGE:`で明示する。
5. 秘密情報、生成物、大きなバイナリ、無関係な変更など、コミットすべきでない可能性がある変更は勝手に除外しない。「除外候補」と理由を示してユーザーに確認する。
6. 次の列を持つ表で計画を提示する。

| 順番 | コミットメッセージ | 変更内容 | 対象ファイル・hunk | 分割理由・依存関係 | 懸念 |
|---:|---|---|---|---|---|

表の後に「除外候補」と「承認後に行う操作」を短く示す。計画提示だけではindexや作業ツリーを変更しない。

## 承認

実際のコミットには、計画提示後の明示的な実行指示が必要である。「この計画でコミットして」など1回の承認で、計画内の全コミットを順番に作成してよい。

承認前後でstaged差分が変わっていた場合や、実行時に計画変更が必要になった場合はコミットせず、計画を更新して再承認を得る。

## 実行

1. `git diff --cached`を再確認し、承認済み計画の差分と一致することを確かめる。
2. 通常の手作業と同様に、`git restore --staged`で対象変更をunstageし、計画順に必要なファイルまたはhunkだけをstageする。作業ツリーの内容は変更しない。
3. 各コミット直前に`git diff --cached`を読み、計画対象だけがstageされていることを確認してから、計画したメッセージでコミットする。同じhunkにstaged対象と元からのunstaged変更が混在するなど、安全に分割できない場合は停止して確認する。
4. Git hookは回避しない。hookやコミットが失敗した場合は後続処理を止め、成功済みコミットをrollbackせず、現在のHEAD、staged、unstaged状態を報告する。
5. 承認済みの除外変更は、全コミット完了後に元どおりstageする。未ステージだった変更を混入させない。
6. 完了後、作成したコミットを順番に示し、残っているstaged・unstaged変更を報告する。

## 境界

- unstaged変更は計画対象にせず、勝手にstage、編集、破棄しない。
- 分割のためのindex操作を除き、コードや設定ファイルは編集しない。成立に補完修正が必要なら、内容を提案して別途承認を得る。
- `--no-verify`、`commit --amend`、rebase、既存コミットの書き換え、コミット後の自動resetは行わない。
