# Code Review Learn

自分の PR に付いたレビューを取得し、`review/<owner>/<repo>/` に溜める。
ここで作る `summary.md` を、`code-review` スキルが追加のレビュー観点として読む。
同じ指摘を何度も受けないようにするのが目的なので、「次のレビューで確認できる形」にまとめることを優先する。

`review/` は社内のコードやレビューのやり取りを含むため、`.gitignore` で除外している。コミットしないこと。

## フォルダ構成

```
code-review-learn/
├── SKILL.md
├── scripts/
│   ├── fetch_reviews.sh   # PR とコメントを取得して JSON で保存
│   └── show_threads.sh    # 保存した JSON をスレッド単位のテキストにする
└── review/                # .gitignore 済み
    └── <owner>/<repo>/
        ├── state.json     # 最後に取得した PR のクローズ日時、未要約の PR 番号
        ├── prs/<番号>.json # PR ごとの生データ(reviews / review_comments / issue_comments)
        └── summary.md     # レビュー観点と PR 別の記録
```

## 手順

### 1. リポジトリを決める

対象は `owner/repo` の形で明示してもらう。指定がなければ、カレントディレクトリのリポジトリ(`gh repo view --json nameWithOwner -q .nameWithOwner`)を候補として示し、それでよいか確認する。
推測で決めないのは、別リポジトリの指摘が混ざると code-review が的外れな観点を持ち込むため。

### 2. 取得する

```bash
<このスキルのディレクトリ>/scripts/fetch_reviews.sh <owner/repo>
```

- 自分が作成したクローズ済み(マージ済みを含む)の PR が対象。レビューが終わった PR だけを学ぶため、オープン中の PR は取らない。
- 2 回目以降は `state.json` の `last_closed_at` 以降にクローズされた PR だけを取得する。保存済みの PR はスキップする。
- 初回は最新 100 件まで。もっと遡りたいと言われたら `--since 2026-01-01T00:00:00Z` や `--limit 300` を付ける。
- 標準出力に今回保存した PR の一覧が出る。0 件なら「新しい PR はありませんでした」と伝え、手順 3 は `state.json` の `unsummarized` が残っている場合だけ行う。

### 3. 要約する

`state.json` の `unsummarized` にある PR を 1 件ずつ処理する。

```bash
<このスキルのディレクトリ>/scripts/show_threads.sh review/<owner>/<repo>/prs/<番号>.json
```

スレッドを読み、残す指摘を選ぶ。PR が多いときはサブエージェントに分けて読ませてよいが、`summary.md` への書き込みはこのスキルを実行している本体で行う(サブエージェントは報告用の .md を書けないことがあるため、要約の内容をテキストで返させる)。

**残すもの**
- 人のレビュアーの指摘(バグ、設計、命名、テスト、アクセシビリティ、ローカライズ、パフォーマンスなど)
- bot(`user_type` が `Bot`、`coderabbitai[bot]` など)の指摘のうち、実際に修正したもの

- 会話コメントに番号付きの箇条書きで書かれたレビュー(人のレビュアーが AI のレビュー結果を貼ったものを含む)。`user_type` が `User` なら人の指摘として扱い、引用付きの返信から解決の方法を読む

**残さないもの**
- bot が取り下げた指摘、自分が反論して相手が納得した指摘(ただし「なぜ不要だったか」が次に役立つなら一言残す)
- bot の指摘で、誰も返信しておらず直したかどうか分からないもの
- 「LGTM」「ありがとうございます」などのあいさつ、CI やレビュー枠の自動メッセージ
- 自分(PR 作成者、JSON の `author`)自身のコメント。ただし返信は「解決の方法」を知る手がかりとして読む

「解決の方法」は、返信や後続のやり取りから読み取る。「修正しました」だけで中身が分からないときは、指摘内容から推測できる範囲で書き、推測なら「(推測)」と付ける。別 PR や別チケットに回したものは「別対応(理由)」と書く。

### 4. summary.md を更新する

`review/<owner>/<repo>/summary.md` を次の形式で更新する。ファイルがなければ作る。

```markdown
# <owner/repo> レビュー学習

最終更新: YYYY-MM-DD / 学習済み PR: N 件

## よく受ける指摘

2 つ以上の PR で受けた指摘。回数の多い順。code-review はここを最優先で確認する。

| 回数 | 指摘 | 次に出す前にやること | PR |
|---|---|---|---|
| 3 | 新しい宣言に doc コメントが無い | 差分の追加宣言を一覧にして、すべてに `///` があるか見る | #7772, #7815, #7914 |

## レビュー観点

code-review がそのまま使うチェックリスト。PR 別の記録から抽出し、似た指摘は 1 項目にまとめる。

### <言語やテーマ(例: Swift / UIKit、ローカライズ、テスト、コミット・PR の進め方)>
- **<確認すること>**(<回数> 回: #7815, #7914)
  例: <実際の指摘を 1 行で>

## PR 別の記録

### #<番号> <タイトル>
- いつ: YYYY-MM-DD マージ(またはクローズ)
- 言語: Swift, xcstrings

| # | 問題点 | 解決の方法 | 指摘者 |
|---|---|---|---|
| 1 | <何がまずかったか(ファイル名など)> | <どう直したか> | <ユーザー名> |

<補足があれば表の下に 1〜2 行で書く(取り下げられた指摘など)>
```

書き方の注意:
- 「PR 別の記録」は新しい PR を上に足す。既存の記録は書き換えない。
- 表のセルは 1 行で書く。改行が要るときは `<br>` を使い、セル内の `|` は `\|` にする。
- 指摘が 1 件もない PR も表の代わりに「指摘なし」として記録する(どの PR を学習済みか分かるようにするため)。
- 似たミスは 1 項目にまとめる。ファイルや書き方が違っても、原因が同じなら同じ項目にする(例: 「型に doc が無い」「init に doc が無い」「enum の case に doc が無い」→「新しい宣言に doc コメントが無い」)。項目を細かく分けすぎると回数が数えられず、「よく受ける指摘」が見えなくなる。
- 回数は「その指摘を受けた PR の数」。同じ PR の中で何度も指摘されても 1 回と数える(何度も指摘されたことは PR 別の記録に書く)。
- 「レビュー観点」は毎回見直す。新しい指摘が既存の項目と同じ趣旨なら回数と PR 番号を増やし、新しい趣旨なら項目を足す。回数が多いものを各見出しの上に置く。
- 「よく受ける指摘」は、「レビュー観点」で回数が 2 回以上の項目から作り直す。「次に出す前にやること」には、PR を出す前に自分で確かめられる具体的な手順を書く。
- コードではなく進め方の指摘(コミットが単体でビルドできない、列挙された指摘の一部を直し漏らした、など)も残す。「コミット・PR の進め方」の見出しにまとめる。
- 日付は日本時間(JST)で書く。
- 「レビュー観点」は「〜を確認する」「〜になっていないか」のように、レビュー時にそのまま確認できる形で書く。個別の行番号や一時的な事情は入れない。
- 言語は `extensions` と変更ファイルから判断する(`swift` → Swift、`xcstrings` → 文字列リソースなど)。

### 5. state.json を更新する

要約した PR 番号を `unsummarized` から外す。

```bash
cd review/<owner>/<repo>
jq --argjson done '[7815, 7914]' '.unsummarized -= $done' state.json > state.tmp && mv state.tmp state.json
```

### 6. 結果を伝える

- 今回取得した PR の件数(手順 2 を飛ばしたときは「取得なし」)と、要約した PR の件数
- 「よく受ける指摘」の上位 3 件と、今回新しく「よく受ける指摘」に入った項目
- 「レビュー観点」に追加・更新した項目(新しく増えたものを中心に、数行で)
- `summary.md` のパス
